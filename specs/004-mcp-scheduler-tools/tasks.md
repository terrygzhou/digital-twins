## Notes

- **One executor (R7):** every tool body lives behind `dispatch` (T010); the stdio and HTTP adapters (T026/T027) differ only in how they receive the request and read the bearer token — they never own tool logic, audit, or role checks. This is what makes transport parity a property of the build, not two hand-kept-in-sync copies.
- **Two distinct audit writes (R3/R8), never conflated:** `kb_schedule_run` → one pipeline-owned `audit_runs` row (`trigger='mcp'`, `agent_kind` in JSON); `kb_run_history` admin cross-user read → one **access-log** row (fresh uuid4, `status='ok'`, `per_source_counts` carrying the `mcp_history_query` block). Own-history reads and schedule CRUD (create/update/delete) write **no** `audit_runs` row (R11); the `kb_run_history` read path excludes `mcp_history_query` rows (R13) so the access-log row is never mistaken for a run.
- **No schema change:** 004 adds no table, no column, no migration. `schedule.acl` (already in 002 DDL_V2, default `'owner'`) is consumed, not added; `agent_kind` rides in the existing `per_source_counts` JSON (D6); `can_access_schedule` is a pure predicate, not a table (data-model.md).
- **Backward-compat invariants:** `mcp_authenticator` is a new, richer `(bool, email)` checker (additive — 003's `auth_checker` `bool|str` is untouched and still gates `serve /status` + the web UI); `run_pipeline` is unchanged (004 calls it with the existing `owner=`/`trigger=`/`scheduled_by=` kwargs); `schedules`/`audit_runs` are read/written only via the shipped 002/003 helpers.
- **Host neutrality (I/NFR-13):** `DT_MCP_TOKEN` is an auth-only env var (read from `os.environ`, never in argv/logs); the HTTP bind address (`127.0.0.1`) and `mcp.port` (`8770`) are config-resolved, never hardcoded host values; the state DB path is config-resolved.
- **Task IDs are feature-scoped** (this file), matching 001/002/003's ledger convention; the SDD ledger (`.superpowers/sdd/`) tracks execution.
