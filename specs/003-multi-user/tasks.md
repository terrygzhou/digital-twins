# Tasks: Multi-User Sign-Up, Roles & Per-User Surfaces

**Feature**: `specs/003-multi-user` · **Constitution**: Test-First (III) — every implementation task has its red test first and fails before it passes.

**Baseline**: 001/002 code paths continue to work verbatim. 003 is additive-only: an optional `owner=` kwarg on `run_pipeline`, an optional `auth_checker` on `StatusServer`, two new `accounts` columns with defaults, and three new tables. No 001/002 call site breaks.

## Dependency Graph (user story completion order)

```
Phase 1 (Foundational: v3 migration + account/role/credential primitives)
   1. migration v3 (data-model.md)                      <- nothing
   2. accounts.py CRUD + last_admin_guard               <- (1)
   3. ROLE_CAPS + test_roles matrix (SC-001)            <- (2)
   4. personal_tokens + auth token helpers              <- (1)
   5. sessions + auth session helpers                   <- (1)
   6. role guard (HTTP/CLI) + last-admin enforcement    <- (3),(2)

Phase 2 (Identity surfaces — sign-in everywhere)
   7.  init first-admin step (C-4)                       <- (2)
   8.  CLI signup / account / token groups               <- (2),(3),(4)
   9.  run --as + schedule post-auth role check          <- (3)  [guard uses ROLE_CAPS]
   10. C-5 auth_checker + StatusServer hook              <- (4),(5)  [checker looks up tokens/sessions]
   11. web /signup + /signin (session tokens)            <- (5),(10)

Phase 3 (Per-user workspace — config + owner tag)
   12. user_config.py merge (R5/SC-003)                 <- (1)   [reads user_config table]
   13. run_pipeline owner= kwarg (R6/SC-005)           <- nothing (pure kwarg)
   14. serve tick: merge + pass owner                  <- (12),(13)
   15. CLI config set/list/unset (per-user overrides)   <- (12),(3)
   16. run-history "mine" filter (audit_runs WHERE scheduled_by = <user>) <- (2)

Polish (cross-cutting)
   17. docs/multi-user.md (roles, tokens, config, owner tags)
   18. quickstart scenarios verified end-to-end
   19. v2->v3 upgrade test + owner-isolation integration test
   20. standing guards green + version bump 0.2.0 -> 0.3.0
```

Critical path: **1 → 2 → 3 → 9** (migration → accounts → roles → the guard that `run`/`schedule` use). Phase 2 and Phase 3 are parallel after Phase 1. The cross-phase join is Phase 3 item 14 (serve merge), which needs both the `user_config` merge (12) and the `owner` kwarg (13).

## Phase 2: Identity surfaces — sign-in everywhere

- [x] **T008** `[US1]` `[P]` — `cli.py::init` first-admin step (C-4/R7): after the state DB is migrated, if `accounts` is empty, prompt for email + password (or read `INIT_ADMIN_EMAIL`/`INIT_ADMIN_PASSWORD` env vars, auth-only, never in argv/logs) and create the first account as `admin` via the shared `create_account` helper; echo "created first admin account `<email>`". If `accounts` is non-empty, do **not** create an account; echo "admin already exists: `<first-email>`" and skip (idempotent). Red test first: `init` on an empty DB creates an admin; a re-run of `init` does not create a second admin (US1 S1, idempotency). **T003 blocks T008.**
- [x] **T009** `[US1]` `[P]` — `cli.py::signup --email E --password P`: create an account; role resolved by the shared helper (first row → admin, else reader); duplicate email → exit 2, "account already exists: `<email>`", no second row. The password is hashed with 001's `hash_password` (R1); `created_at`/`last_active` set to now. Red test first: first `signup` on a fresh DB is admin, second is reader, duplicate email fails with exit 2 and no second row. **T003 blocks T009.**
- [x] **T010** `[US3]` `[P]` — `cli.py::token create|list|revoke` (self-service or admin): `token create [--as USER]` (without `--as`: the caller's own token, any authenticated role; with `--as USER`: admin-only, create for another user) prints the plaintext token once; `token list [--as USER]` (self: own; admin: any) lists `id`, `created_at`, `last_used_at`, `revoked` (plaintext never re-displayed); `token revoke --id N` (self: own tokens only; admin: any) flips `revoked=1` on that row only. All three authenticate first (password or personal token via `DT_PERSONAL_TOKEN`), then check the caller's role against R3 (manage own personal tokens: admin/scheduler/reader for *their own*; admin for another user's). Red test first: create a token, list shows it (no plaintext), revoke flips `revoked`, a reader cannot create a token for another user (exit 2, named reason). **T005 and T004 block T010.**
- [x] **T011** `[US2]` `[P]` — `cli.py::account list|set-role|delete|whoami`: `account list` (admin only; `email`, `role`, `created_at`, `last_active`), `account set-role --email E --role {admin|scheduler|reader}` (admin only; last-admin guard SC-002 — refuse with exit 1 "cannot demote the last admin" if it would leave zero admins; otherwise apply + record in the audit trail), `account delete --email E` (admin only; same last-admin guard; cascades to `personal_tokens`/`sessions` via FK `ON DELETE CASCADE`), `account whoami` (authenticated, any role — print caller identity + role; the only non-admin-gated subcommand). All authenticate first (password or personal token), then check R3 (account management: admin only, except `whoami`). Red test first: a reader calling `account list` → exit 2 "role `reader` may not manage accounts"; a scheduler calling `account set-role` → exit 2; the last-admin demote/delete both refused (exit 1); `account whoami` works for a reader (prints identity + role). **T003, T004, T007 block T011.**
- [x] **T012** `[US4]` — `cli.py::run --once --as USER` + `cli.py::schedule add|list|remove` post-auth role check (C-2): after `authenticate(db, USER, DT_USER_PASSWORD)` (or the personal-token resolve via `DT_PERSONAL_TOKEN`) succeeds, the caller's role must permit **trigger a run** (`run --once`) or **schedule CRUD** (`schedule`). On denial: exit 2, stderr names the insufficiency ("role `reader` may not trigger a run" / "role `reader` may not manage schedules"), **no** audit row, **no** Qdrant write, **no** high-water advance, **no** schedule row written. On success: `scheduled_by = USER` (002) and the run's points carry `owner = USER` (R6 — see T013/T014). Red test first: a reader's `run --once --as` → exit 2 with named reason and zero ingestion; a scheduler's `schedule add` succeeds; a reader's `schedule add` → exit 2 before any row is written. **T004 and T007 block T012.**
- [x] **T013** `[US4]` — `scheduler/status.py`: `StatusServer.__init__` gains an optional `auth_checker=None` kwarg (C-5/R8); `do_GET` wraps the check *only when* `auth_checker` is not None. Return semantics: `True` → allow (200), a `str` → deny with that string as the 403 body error, `False` → deny with a generic "unauthorized" (401). The serve CLI (`cli.py::serve`) builds a `_auth_checker(db, service_token_env)` that accepts, in order: (1) the shared service token (`DT_SERVICE_TOKEN`, constant-time compare), (2) a valid personal token (`personal_tokens.verify`), (3) a valid session token (`sessions.verify`); no/unknown credential → `False` (401). Red test first: a `StatusServer` **without** `auth_checker` (002's callers) returns 200 on `/status` with no auth check (C-5 backward-compat); with a checker, no credential → 401, service token → 200, a personal token → 200, a session token → 200, an unknown Bearer → 401. **T005 and T006 block T013.**
- [x] **T014** `[US4]` — `web/server.py` (new `digital_twins.web` package): `ThreadingHTTPServer` with `POST /signup` `{email, password}` → `200 {"email","role","created":true}` (role = first row? admin : reader, shared with CLI signup; duplicate email → `409 {"error":"account already exists"}`; password hashed with 001 `hash_password`, R1) and `POST /signin` `{email, password}` → `200 {"session_token","expires_at"}` (authenticates via 001 `auth.authenticate`; on success creates a 32-byte session token, stores its pbkdf2 hash in `sessions`, returns the **plaintext** token once; sets `accounts.last_active`; on failure → 401). Red test first (via `http.client` against a `ThreadingHTTPServer`): `/signup` on an empty DB returns `role=admin`, a second `/signup` returns `role=reader`, a duplicate email returns 409; `/signin` with valid credentials returns a session token that the C-5 `auth_checker` accepts on a subsequent request; `/signin` with a bad password returns 401. **T006 and T013 block T014.**

## Phase 3: Per-user workspace — config + owner tag

- [x] **T016** `[US5]` — `ingest/pipeline.py::run_pipeline` gains an optional `owner: str | None = None` kwarg (R6): when set, each point's Qdrant payload gains `"owner": owner` and `"owner_tag": f"{owner}-ingest"`; when `None` (default), the payload is unchanged (001/002 behavior). - [x] **T017** `[US3][US5]` — `scheduler/loop.py::serve_once_tick`: for each due schedule, merge the schedule owner's `user_config` overrides into a **copy** of the global config via `merge_user_config` (C-3, never mutate the shared global) and pass `owner=schedule["owner"]` to `run_pipeline` (R6). - [x] **T018** `[US3]` `[P]` — `cli.py::config set|list|unset` (per-user overrides, R5): `config set --as USER --source S --key K --value V` (set a per-user override; the role must permit **manage own personal config** — admin/scheduler/reader for *their own* user; admin for another user's; `K` restricted to the overridable keys, other keys → exit 2; `V` type-coerced via 001 `schema.coerce` at write time, fail-fast on a malformed value), `config list --as USER` (list a user's overrides), `config unset --as USER --source S --key K` (remove one). - [x] **T019** `[US3]` `[P]` — Run-history "mine" filter: a `list_runs(db, user=None, all_users=False)` helper that queries `audit_runs WHERE scheduled_by = <user>` (the "mine" view: a user's own account or a manual/MCP trigger attributed to them); `all_users=True` (admin only) returns every row. ## Notes

- **Parallel pairs**: T008 ∥ T009 ∥ T010 ∥ T011 (all are CLI identity surfaces that share T003/T004 but not each other); T018 ∥ T019 (per-user config and run-history are independent reads/writes over the same `user_config`/`audit_runs` tables); Phase 2 and Phase 3 may interleave once Phase 1 lands.
- **No host paths anywhere**: `INIT_ADMIN_EMAIL`, `DT_PERSONAL_TOKEN`, `DT_SERVICE_TOKEN`, and the `docs/` content are all host-neutral (SC-006 guard is authoritative). The four credential env vars are auth-only, read directly from `os.environ`, never in argv, never in logs (R9).
- **Backward-compat invariants**: `run_pipeline` gains an optional `owner=` kwarg (default `None` = legacy); `StatusServer` gains an optional `auth_checker` kwarg (default `None` = 002 behavior); `accounts` gains two columns with `''` defaults; `auth.authenticate` is untouched. 001's portability + one-record guards (SC-006) re-run at T024.
- **Task IDs are feature-scoped** (this file), matching 001/002's ledger convention; the SDD ledger (`.superpowers/sdd/`) tracks execution.
